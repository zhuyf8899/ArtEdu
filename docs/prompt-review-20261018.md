# 本地提示词审阅与源码阅读索引

审阅时间：2026-10-18。范围：当前工作区业务源码中的固定系统提示、动态执行指令、工具说明、历史记忆、文档生成、工作流文本节点和本地 Bridge。历史沙箱、测试夹具不作为生产规则。未读取服务器/数据库中用户保存的任意提示词实例，未调用外部模型。初稿为静态审阅；随后已按用户要求实施下述修复。

## 已实施修复（后续更新）

- 客户端 system/tool 历史降级为标明来源的用户参考数据；附件不再作为 system 消息。兼容 systemPrompt 仅作用户级格式偏好。
- 后续提问走独立单次调用（最多500输出token），不带工具或任务补齐提示，并校验三条唯一问题。
- 删除全局SVG诱导与“批量全部写入”的旧规则；统一写入自动建父目录、按预算分批，不再固定1800字符。工具说明如实描述浏览器可选检查。
- 多格式文档和多张图片按交付数量验收；成功调用按规范化参数去重，允许不同目标再次调用同类工具。没有宣称解决任意自然语言下的精确计划解析。
- generate_image 新增 workspacePath，读取当前新生成任务的真实私有产物，将二进制安全保存至工作区；自动匹配扩展名，网页可相对引用。浏览器检查支持PNG/JPEG/WebP/GIF/AVIF及图片加载验证。
- Word/PDF使用长文结构（最多40节、每节20段、每段1200字），PPT保留原版式约束；解析、修复提示和导出使用一致的格式规则。当前仍只有章节、段落、要点，不支持复杂表格/插图版式。
- 本地Bridge沿用服务端合成提示与历史，移除旧“固定四节方案”提示；明确只支持文本。服务端拒绝将产物创建任务派给这个不具工具能力的Bridge。没有新增本地工具代理，也没有把服务端密钥传给本地。
- 一般问答不再硬套三段结构与600字；课程创作可以按依赖读取，课件事实与一般建议分开。复盘明确缺少工具证据，不得从自述提炼已验证技能。

验证：后端176项、前端187项、原有11例业务回归、2例真实Harness链路回归、Bridge消息构造测试通过；两端构建通过。模型均为夹具，未消耗外部API额度。新图片回归使用真实PNG字节与本地隔离Chrome，不等同于供应商生图质量测试。

原始发现保留在下文用于解释修改原因，不表示仍未修复。工作流promptTemplate目前明确是未来功能，未将数据库中的模板擅自启用为高优先级指令。

## 已确认的问题（按影响排序）

### 1. 客户端内容被提升到 system 指令层（高）
agent.contracts.ts 13 行允许 context 的 system/tool 角色，harness 165/223 行直接保留角色；169 行又把客户端 systemPrompt 拼进真正系统提示。前端记忆也用 system 传输。声明“不得覆盖”只是文本约束，无法替代来源隔离。
影响：压缩历史、伪造工具结果、附件摘录与客户端格式偏好有机会改变模型任务判断；服务器权限检查仍有效，不能据此声称已绕过权限。
建议：服务端保留可信系统规则；客户端历史限制 user/assistant；工具结果由服务端生成；记忆作为有来源、无指令权的数据注入。真实使用服务端签名产物记录，而非信任客户端产物声明。

### 2. 本地 Bridge 忽略服务端合成提示和历史（高）
bridge.mjs 20/27 行自建“把需求转成方案”提示，只发送 agentPrompt 与当前用户需求；没有使用服务端附加的 systemPrompt/context，也没有平台工具循环。chat/document_generation 未在本地角色映射中定义，会出现“你是undefined”。
影响：相同输入切到 local 后，工具执行、参考历史、创建文件等能力与 server 完全不同。这是实现差异，不能靠润色一句提示解决。
建议：明确本地支持能力并统一协议，或实现受控工具桥接；补齐所有场景角色。

### 3. 系统规则和工具说明相互打架（中高）
policy 要求“每次只写一个文件”“无需创建目录”；create_workspace_directory 的说明却要求多文件网页先建目录，write_workspace_files 又鼓励一次一组。全局原文“一次写全部文件”通过字符串 replace 临时消除，后续改字就可能失效。
影响：不必要的目录和批量写入调用、截断重试、模型不确定该听哪一层。
建议：规则由一个来源生成；工具描述讲能力与参数，执行策略按任务和预算注入。

### 4. 图片与网页的混合交付缺少资产接入说明和工具（中高）
generate_image 返回站内私有图片 URL；网页预览要求同目录相对资产且禁止绝对/外部地址。当前没有把生成图片导入工作区的专用工具。给模型同时要求“真实生图并嵌入网页”，却没有清楚可执行的连接步骤。
影响：模型可能反复尝试地址、用占位图或 SVG 替代；这是能力缺口，不只是提示词问题。
建议：提供受控的生成产物导入工具，或统一预览资产代理；成功导入后再允许页面验收。

### 5. 文档统一套用短幻灯片结构（中高）
documentPrompt 对所有格式都限制 1–11 节、每节最多360字、两段、无表格与图片字段。PPT 的版式约束适用于幻灯片，直接套 Word/PDF 会限制长文、完整教案、复杂讲义。
影响：工具确实生成文件，但内容可能过短、过浅，无法满足用户“完整文档”的要求。
建议：按格式和文档类型分 schema/预算；明确不支持的版式；保持真实正文与校验，不以删内容作为通用修复策略。

### 6. 提示词所描述的能力已经落后于实现（中）
harness 与 check_page 工具描述仍说“只做静态检查”，但实际支持可选浏览器检查；是否通过应依据工具返回的 scope/available。
generation.service.ts 的通用 chat 提示要求用户切换能力才能生成，而 Agent 已可跨类型执行；通用创作提示一律“只输出方案”。它们属于不同入口，不能直接断言这段导致当前 server Agent 不生图。图片适配器只取最后 user 提示，因此通用方案 system 文本并没有实际发送进图片生成 prompt。
建议：区分入口职责，按真实能力生成说明；不要将旧入口文案当成 Agent 当前行为证据。

### 7. 每个网页文件1800字符的固定限制与预算不匹配（中）
policy 与循环反复强调单文件1800字符，同时默认最多8轮且最后一轮禁用工具。
影响：复杂页面被迫压缩代码或拆过多文件，挤占读取、修复、检查次数；展示质量下降并不一定是模型审美问题。
建议：使用剩余 token/任务规模计算预算，允许合理批次；保留完整参数检查和阶段性验收。

### 8. 合同“只识别一份”与模型请求不一定一致（中）
planTask 以正则产生合同，document 只选一个格式；循环按工具名而非交付目标去重，一次 generate_document/image 成功后隐藏该工具。后续提示“不要重复生成已有文档或图片”无法区分重复与用户要求的第二份。
影响：多张图片、同时 Word+PDF、修改已有图片可能被错误约束；应修复计划/执行逻辑，不能只增加一句“认真理解用户”。
建议：交付项有稳定ID、数量、格式与版本，按目标去重。前端 taskIntent 与服务端 planner 避免维护两套分叉规则。

### 9. 后续问题请求仍被套入完整 Agent 编排（中）
Portal 只要 JSON 三个问题，但 harness 依然拼全局平台/工作区规则和任务合同，运行循环继续追加进度；工具已被关闭。
影响：增加 token 和相互无关的指令，回答正文中的生成语句可能误触任务分类并产生无工具可补齐的重试。此失败路径尚未做真实模型复现，属于代码路径风险。
建议：独立轻量结构化请求，不经交付循环，限制一次调用并校验三条字符串。

### 10. 固定格式与知识边界过度统一（低到中）
通用问答固定“结论、依据、做法”和600字；本地所有任务固定四个小节；课件回答“只能依据摘录”有助防伪，但缺少“资料事实”与“一般知识补充”的区分；检索只允许用户明确问平台内容，可能妨碍依赖课程资料的创作请求。
建议：按任务选择输出格式，事实引用与建议分开；根据任务依赖允许读取，避免每次都先给方案或先澄清。

## 其他提示来源与边界

- 附件：harness 以 system 消息携带不可信文件内容，虽有警告，仍建议数据角色化、明确来源边界。
- 网页检索：有外部不可信数据声明与真实链接要求，方向合理；不能保证所有平台数据库内容也有同样边界。
- 本地复盘：learningPrompt 禁止记录密钥与未验证事实，候选条目带 reviewRequired；但输入只有输出摘要，没有工具证据，不能靠模型自述将其升级为已验证技能。
- 工作流 promptTemplate：检索业务源码只看到保存与返回，没有 executeNode 消费；UI 本身写了“供未来模型节点调用”。因此当前不是生效的全局提示，不应期待编辑后影响生成。
- 工作流默认正向“主体明确”等过于泛化、负向默认排除文字不适合所有海报；它们是可编辑样例，是否实际生效取决于具体工作流数据，未读取数据库逐项评审。
- 历史 sandbox policy、audit scripts、model-harness 中的测试 system，不属于当前业务提示。后续改动应修改业务源码，不能只改沙箱副本。

## 建议处理顺序

先统一可信指令与数据来源、本地/服务端能力协议；再合并矛盾的工具说明与动态规则，补齐混合资产路径；之后按任务拆文档结构、预算、后续问题请求。每项都要用具体反例验证，不能把“提示更多、更长”视作修复。
