# 本地首轮接口压测结果

采集环境：Intel(R) Core(TM) Ultra 9 275HX，24逻辑CPU，宿主内存31.36GiB。compiled native Windows Node, no Nginx, dedicated Docker PostgreSQL。

k6退出码：0；采样38次。默认池大小10，数据为独立演示库与300个测试账号。

这是一轮有思考停顿的虚拟用户阶梯测试，不是300个同时在途请求，也不是浏览器渲染测试。30秒升压，300用户保持180秒，再用20秒降压。合成目录为15门课程、14个案例，未复制真实媒体文件。未包含媒体下载、RAG、真实模型、GPU、文档导出、Nginx和公网带宽；小规模演示库不同于实际数据规模。不能据此承诺云服务器同等并发容量。

补充核对：专用数据库包含15门课程、14个合成案例、300个测试账号和300个会话；最终学习笔记1466条（含前一轮被用户切换前的测试记录）。数据库容器restart=0、OOMKilled=false。本轮11247个完整操作循环、0个中断循环，总耗时约4分06秒（含登录setup和降压收尾），HTTP请求50816次，其中业务负载50515次。仅接口响应数据约292MB，平均约1.2MB/s，接近10Mbps理论总吞吐；本机回环网络没有公网带宽约束，不能把这一延迟直接映射到10Mbps云服务器。

运行方式与生产差异：Windows Node v24编译产物直连API；数据库在Docker Linux容器，Docker可用24逻辑CPU、约15.3GiB，宿主内存31.36GiB。NODE_ENV=test以使用隔离本地认证，日志比当前staging少；模型及RAG关闭；数据库连接池10。压测机和API在同一台电脑，不含Nginx、TLS、页面资源/浏览器渲染、媒体下载、集中并发登录、真实模型/SSE与GPU。每用户一轮约3–8秒，测试模拟的是300位在线用户交替操作，不是300个始终同时在途的HTTP请求，也不是300个同时生成的Agent。

只在专用preload提高每IP限额，原生产模块未改。原生产每IP读120/分、写30/分，需要另行校验校园共享出口/反向代理下的限流和真实IP策略。本轮没有验证该策略能接纳300人。

150人阶梯被用户中途要求切换，日志保留于local-artifacts/loadtest/partial-150，不能称为完整通过。300人结果日志、汇总和资源快照在local-artifacts/loadtest，账号凭据仅保存在忽略目录。执行工具已停止加压，隔离测试API和数据库暂留用于复查；未部署或压测Ubuntu服务器。

结论：本机基础业务接口通过300个在线虚拟用户的短时初筛；不构成云端完整网页或300人同时Agent调用的稳定容量承诺。下一轮应在接近目标配置的Linux/Nginx栈上，加入媒体和真实数据体量、Agent长连接与更长保持时段。
