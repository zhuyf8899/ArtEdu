# Agent 提示词、任务执行与展示审查（2026-10-18）

审查对象：当前工作区源码，含已有未提交改动；不是只审阅 Git HEAD。未改动生产逻辑、用户数据或线上部署。新增了一个隔离测试驱动：`apps/api/scripts/audit-agent-20261018.ts`。

## 结论与证据边界

目前的主要瓶颈是提示词入口、任务分流、完成判定、会话记忆和显示契约之间没有形成一致的任务闭环。仅更换模型或增加一段“请认真完成任务”的提示词不能解决这些结构问题。

- 新增 76 项针对性探针：40 项任务分流样本，36 项提示词/执行/状态/上下文/结果渲染/传输探针。
- 40 项分流中有 27 项与人工标注的目标分流不一致。这是特意选择的边界与对抗样本，**不能解释为真实用户总体错误率 67.5%**。其中网页类回退 chat 仍可能调用工作区工具，不等同于最终任务必然失败；误入图片/文档直连则会实际改变执行通道。
- 76 项中记录了 51 项不匹配观察，存在重复根因和设计能力差异，**不是 51 个独立缺陷**。
- 现有后端相关回归 28/28、前端相关回归 32/32 通过。新增探针与旧测试同时成立：旧测试没有覆盖下面的任务完成条件。
- 编排测试直接调用真实 `AgentHarnessService`、`runModelLoop` 和 `executePlatformTool`，仅模型、数据库和工作区替换为内存实现。脚本模型是按预设序列发出工具调用，证明的是系统如何处理这些输出，**不能证明真实模型必然产生相同输出**。
- 实际调用了生产代码中的路由函数、状态函数、上下文函数、Markdown 服务端渲染和 SSE 解析器；没有进行浏览器布局、视觉质量或真实低配机性能测试。
- 外部模型测试最初被自动审批拦截；用户随后明确授权，已完成 8 组对照及其中一组剩余额度内的 2 次协议诊断。合计 30 次模型适配器调用，任一组累计不超过 5 次，每次 maxTokens=2400；真实测试结果见文末补充。

原始证据：`local-artifacts/agent-audit-20261018/deterministic.json`；有效提示词快照：同目录的 `frontend-effective-prompt.txt`、`server-default-prompt.txt`；源码摘要：`source-hashes.json`。

## 1. 正常前端路径把完整服务端提示词覆盖掉（最高优先级）

位置：`admin-console/src/Portal.jsx:165`、`apps/api/src/modules/agent/agent-harness.service.ts:166`。

后端使用 `input.systemPrompt ?? 默认完整提示词`。前端传入的并非附加要求，却被当作完整替代。隔离捕获的网页任务默认提示词 1,682 字符，正常前端有效提示词只有 236 字符，丢失了工作区写文件、离线资源、SVG、文件引用和 `check_page` 自检规则。

直接影响：这些规则虽然在代码里看得到、也可能通过“源码含有 check_page”的测试，但用户从 `/create` 发起任务时并没有交给模型。旧 `/morph/chat.html` 不传这个覆盖字段，反而使用另一套默认规则，两个入口行为不一致。

修复方向：服务端拥有不可被客户端替换的基础策略；客户端只传结构化意图、联网偏好与输出约束。需要补充说明时作为受约束的任务上下文，不能替换基础策略。

## 2. 提示词的交付目标互相矛盾

位置：`agent-harness.service.ts:22`、`:49`。

`webpage_generation` 场景要求“输出可实施的网页构建说明”，而完整工具策略要求“创建 index.html/CSS/JS 并给预览”。UI 标题又是可运行网页原型。这会把“写说明”与“实际制作”同时放入指令。chat 场景另要求用户明确切换能力才生成文件，但工具列表又提供文档和工作区写入，容易让同义请求因模式不同而出现不同解释。

这不是从真实模型回答中推断的失败概率，而是可直接确认的指令冲突。

修复方向：先区分解释、评审、规划、创建、修改、导出；仅在解释/规划任务输出说明，创建/修改任务必须交付对应产物。UI 的“建议模式”只提供偏好，不替代本轮意图。

## 3. 任务判断主要是无上下文正则，而非 Agent 判断

位置：`admin-console/src/creationMethods.js:94`，首页和创作页都会调用。

典型复现：

| 用户输入 | 当前结果 | 目标行为 |
| --- | --- | --- |
| 不要生成图片，只解释海报构图 | UI 图片通道 | 文本解释 |
| 不要制作网页，先讨论方案 | Word 文档通道 | 文本讨论 |
| 解释 PDF 和 Word 的区别 | PDF 文档通道 | 文本解释 |
| 如何把PPT导出为PDF？ | PPT 通道 | 解释操作方法 |
| 评价这段提示词：生成一张海报 | 图片通道 | 评审引用内容 |
| 翻译“生成一个网页”为英文 | 网页通道 | 翻译 |
| 请生成一份课程方案，直接在对话里回复 | Word 通道 | 直接回复内容 |
| 继续，把按钮改成紫色 | chat | 结合上一轮继续修改网页 |
| 请创建一个 Word 文档和一个网页 | 只进入 Word | 多产物任务编排 |

具体机制：出现 Word/PDF/PPT 单词即可命中文档分支；正则不理解否定、引用、提问和多轮指代；文档分支先匹配会吞掉后续网页或图片需求；函数接受 `advisoryMethodId`，却不使用该参数。

注意：chat Agent 本来拥有写网页/SVG/代码文件工具，因此 chat 回退不必然等于功能不支持；关键问题是没有显式任务计划与统一交付合同，后续依赖模型猜测。

## 4. “模型结束回答”被等同于“用户任务已完成”

位置：`agent-runtime.ts:83`、`agent-harness.service.ts:279`、`agent.service.ts:115`。

模型最后一轮没有 tool call 就退出循环；Harness 保存一份最终文本 JSON 并调用 `completeRun`。没有核对“用户要求网页→必须有 HTML 文件→必须检查→必须返回有效预览”。

隔离复现：

- 模型只说“网页已完成”而未写文件，Run 仍为 succeeded。
- 写了一份没有样式的 HTML，不调用 check_page，仍为 succeeded。
- check_page 明确返回 verdict=fail，模型随后说完成，仍为 succeeded。
- 上游 finishReason=length，内容已截断，仍可标 succeeded；文档直连路径反而有截断检查，Agent 路径没有。

工具出错后模型诚实解释失败，整次“回答请求”可以正常结束；不应该把任何工具失败都机械地判整轮失败。但“回答已结束”与“交付验收通过”必须分别记录。

修复方向：任务维护 requiredDeliverables、实际产物和检查记录；用 succeeded/partial/blocked/failed 表示交付结果。失败检查必须修复或明确归入未完成，不允许仅凭最终文本标完成。

## 5. 工具调用成功、业务检查成功、等待授权混成一种状态

位置：`agent-tools.ts:199`、`:248`、`agent-runtime.ts:95`。

check_page 的工具执行本身返回 `status:succeeded`，但 `verdict:fail`；循环只检查 error 字段或 status=failed，所以 UI 接到工具成功。start_workflow_run 返回 `confirmation_required` 也被循环记录为 succeeded。

确认解析又依赖精确词边界：`确认启动工作流` 不通过，`确认，启动工作流` 才通过；孤立的“同意”不绑定具体 workflowId。不能据此声称有完整的用户确认状态机。

修复方向：区分 transportStatus 与 outcome；增加 needs_confirmation、validation_failed；授权绑定到动作、对象与参数，并支持会话内对应的确认回复，不能全靠一句正则。

## 6. 固定 8 轮没有给最后总结留预算，也没有可恢复执行状态

位置：`agent-harness.service.ts:261`、`agent-runtime.ts:59`。

复现了 7 次工具写入＋第 8 次检查：文件已写入，随后因为没有第 9 轮总结机会而失败。每轮可包含多个 tool call，所以不是“最多 8 个工具”，但复杂任务很容易在修复、重查时耗尽。

当前失败会留下已经写入的文件，却没有结构化告知哪些成功、哪些未完成。前端也没有保存 Agent Run ID 以恢复此循环；刷新恢复主要是把本地 streaming 标记改成暂停。

修复方向：按时间、token 与工具次数设置预算；临近上限进入禁止新工具的收尾阶段，输出部分成果与未完成原因。持久化任务状态和 runId，允许明确的继续执行，不重放已完成的写入。

## 7. 重新输出的界面与模型上下文不一致

位置：`CreationWorkspace.jsx:190`、`:405`。

retryReply 把界面历史截断后作为 baseMessages 传给 generate；generate 却用完整 conversation 调用 makeModelContext。旧错误答案及后续分支仍被发送给模型。

影响：用户以为清除了某轮回复，模型却仍看到旧结论；重试可能继续沿用错误假设或引用用户已经弃用的后续内容。

修复方向：所有重试上下文都从同一份截断后的消息构建，并显式指定附件、产物和记忆的分支版本。

## 8. 长会话压缩损失了执行记忆，且可能再次丢弃压缩记忆

位置：`conversationStore.js:43`、`:56`。

压缩只摘录旧 user 消息，丢弃 assistant 决策、已生成文件路径和工具结果。另一处在把压缩记忆插到首位之后 slice(-30)，当消息数超过限制时，首位记忆自己被裁掉。

复现：52 条消息压缩后，旧产物 `project/index.html` 消失，只剩一组“用户：继续完成页面”；32 条消息构建上下文时，首位重要约束记忆被裁掉。

修复方向：任务记忆独立保存目标、已确认约束、决定、产物清单和验证状态；历史对话截断与任务记忆分开预算；不要将用户摘录直接当作新的高优先级操作指令。

## 9. 展示层没有形成“产物交付”界面

位置：`AiMarkdown.js:17`、`CreationWorkspace.jsx:565`、`Portal.jsx:181`。

AiMarkdown 的 skipHtml 会忽略原始 HTML/SVG；Markdown 图片一律转换成链接；工作区网页结果没有统一映射成 localFile/预览组件。只在最终文本里出现链接时，用户才能找到网页。SSR 探针确认 SVG、工作区图片、网页最终都只剩普通链接或空内容，没有内联预览。

这里不能简单启用任意模型 HTML，否则会绕过现有渲染边界。应该把已验证的站内产物做成独立组件：名称、类型、状态、打开预览、下载、最近修改；图片只内联经平台确认的产物。网页使用现有受限预览策略，不把任意模型文本作为主站 DOM。

同一轮模型在工具调用前输出的说明与最终回答也没有消息边界：增量一直累加，done 时又替换成最后一轮文本。复现了先显示“我先查看文件。最终成果如下。”，结束时变成“最终成果如下。”；这属于协议/展示边界问题。

## 10. 进度事件有了，但 UI 按旧规则隐藏了关键信息

位置：`agentActivity.js:15`、`:19`、`CreationWorkspace.jsx:603`。历史设计依据见 `docs/agent-execution-notices.md`。

当前规则明确要求隐藏任务和模型事件，把每次工具的开始/完成合并，不显示成功/暂停，只标失败。这不是这次审查发现的意外退化，而是此前显示要求的直接结果；与当前“让用户看清任务进度”的目标有冲突。

复现：只进行模型调用时，收到两个事件而显示零条；写入多个文件的 running/succeeded/paused 三种状态显示相同文字；折叠保留首次时间，因此没有直观的完成时刻或持续时间。事件也没有用户可读的阶段、当前对象、等待原因和成果引用。

建议保留简洁主界面：显示当前阶段、当前动作、已完成事项、真实检查结果和等待原因，详细工具日志折叠。不要暴露模型内部推理，也不要编造百分比。

建议事件契约：

```json
{
  "runId": "...",
  "stepId": "...",
  "phase": "create",
  "status": "running",
  "label": "正在创建作品画廊",
  "subject": "index.html",
  "startedAt": "...",
  "endedAt": null,
  "outcome": null,
  "artifactIds": []
}
```

公开字段仅放经过过滤的任务元数据，不放密钥、工具原始参数、用户文件内容或模型推理。

## 11. 两套前端和三条执行路径导致体验不一致

主站：`/create` → CreationWorkspace → Portal → Agent 或 generation-jobs。

旧静态入口：`/morph/chat.html` → connected-chat.js → connected-api.js。

旧入口默认首页模式为 image，聊天模式只有 chat/image；流式解析忽略 progress，内容以转义后的纯文本显示，只有 generation-jobs 下载地址被额外转成链接。工作区预览链接、Markdown 结构和 Agent 执行记录无法获得主站相同的呈现。

图片/图案/文档直连任务目前只有外层开始/完成事件，没有内部进度；不能靠前端猜测实际正在渲染第几页。Agent 内也没有图片生成工具，因此同一任务要求网页＋真实生图时，无法在现有统一工具循环中完成全部子任务。

修复方向：两个入口共享同一个任务客户端、会话与产物契约，或让旧入口清楚引导到主站。把生成任务接入统一任务工具和真实状态流，避免前端先锁死单一产物类别。

## 12. 其他已确认的缺口

- 附件过期时读取异常被吞为 null，但代码没有向模型提供注释所说的“文件缺失说明”，容易诱发无依据回答（harness:155）。
- generate_document 工具把 context 固定为 []，多轮讨论好的内容和附件不会自动传入，依赖模型在 prompt 参数中完整重述（agent-tools:171）。
- 自动追问使用“不要调用工具”的提示词，却仍得到全部 25 个工具并采用 auto；其中包含写文件和启动工作流等工具，能力不需要这么宽。应使用无工具的轻量独立调用。
- harness_probe 本是测试探针，却被提供给正常用户的生产 Agent；应从正常任务工具列表移除。
- 静态 check_page 能通过空 style、CSS url 外链、fetch 外部接口和语法损坏的 JS；这是检查边界，不能把 pass 宣传为视觉/交互验收通过。应增加检查项，并明确静态通过与真实浏览器验证是两种证据。
- 主站 SSE 解析没有规范化 CRLF，合规 CRLF 帧的合成测试失败；旧入口反而有规范化。当前后端输出 LF，因此这是协议兼容缺口，不是已经证明的线上断流根因。
- 模型适配器与文件读取在主 try 之前执行；部分初始化异常可能使 run 在 claim 后未正常归入失败状态，需补充覆盖与清理。

## 修复顺序与验收

1. **先统一提示词和完成合同**：保证每个入口的系统基础策略实际生效；网页生成必须有真实文件和检查记录，截断/未修复检查进入 partial/failed。
2. **再修任务判断与记忆**：否定/解释/引用不误触发产物通道；多轮修改能定位上一轮产物；重试与上下文分支一致；压缩保留任务状态。
3. **再统一事件与交付 UI**：任务阶段、工具结果、等待确认、部分成果和最终成果分别展示；主站与旧入口一致。
4. **最后做真实模型评估和视觉回归**：与原版成对比较，固定模型、任务和初始工作区；记录模型调用、工具序列、产物、静态检查、浏览器渲染及用户可见结果；做多次重复后再估计成功率。

不要只加长提示词，也不要把所有任务强制变为先写计划。普通问答直接回答；明确创建任务直接执行；复杂任务才显示简短可验证的步骤。

## 可复运行的本地机制

在仓库根目录运行，无外部模型调用、无数据库和生产文件写入：

```powershell
apps/api/node_modules/.bin/tsx apps/api/scripts/audit-agent-20261018.ts
```

驱动会使用真实源码重建当前有效提示词、任务分流与工具循环，将模型替换成明确的响应序列，在内存工作区执行写文件、检查和错误恢复；JSON 中每项保留输入、实际状态和关键证据。普通执行退出成功表示“审查探针运行完毕”，不表示被测产品没有缺陷。

已完成 8 组外部模型对照（4 个任务 × 当前/候选提示词）：创建画廊、修改已有网页、修复缺失样式、明确只讨论。每组最多 5 次模型调用，每次最多 2,400 输出 token，工具和文件仍只在内存隔离环境中。以下命令会再次消耗额度，不应因阅读报告自动重跑：

```powershell
apps/api/node_modules/.bin/tsx apps/api/scripts/audit-agent-20261018.ts --live
```

外部测试仅发送合成任务、提示词及模拟文件/工具结果；不发送真实用户文件或生产数据。候选提示词只用于实验，尚未部署；8 组小样本也不能作为总体任务成功率的统计结论。

### 输出预算与 thinking 的具体影响

在 `create-web/candidate` 组剩余额度中追加 2 次单次请求诊断，保持同一合成任务、候选提示词及工具定义。该组原先只用 1 次，总计 3 次，低于授权上限 5 次。

- 供应商默认设置：HTTP 200，但 `finish_reason=length`；2400 completion tokens 中有 2114 reasoning tokens；模型尝试调用 write_workspace_files，参数只有 551 字符且不是合法 JSON。
- 关闭 thinking 的单次诊断：`finish_reason=tool_calls`，37 completion tokens，返回合法的 list_workspace_files 调用，没有推理输出。**这仅证明该次调用没有相同截断，不证明关 thinking 后完整画廊任务必然成功。**

证据保存在 `diagnostic.json`，只保存 token 统计、finish reason、参数长度/JSON 合法性等诊断字段，没有保存或展示内部推理正文。

这项结果说明：严格的 2400 token 测试上限会显著影响开启 thinking 的长代码任务；不能把此次所有失败归咎于提示词，也不能把该失败率直接外推到未设置同样上限的生产任务。同时，它确实暴露了产品未充分区分“推理耗尽输出预算、工具参数截断、模型空响应”的错误呈现问题。工具参数只验证字段存在、没有在适配器入口验证 JSON 完整性，也让错误推迟到执行层。
